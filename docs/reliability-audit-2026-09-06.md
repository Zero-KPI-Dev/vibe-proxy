# Hermes 请求卡住：可靠性与性能白盒审查

基线为 `6844117`，即 `v0.1.0-rc.3` 对应的 main。用户现象是在 Windows
接入 Hermes 后，运行一段时间出现大量请求长时间等待首 token。

没有用户机器的线程栈、上游日志或网络抓包，无法断言现场只有一个原因。
以下问题来自代码路径及故障注入测试；测试不依赖用户的模型服务或密钥。

## 确认的问题及修复

### 1. 下游阻塞可以越过上游超时，长期占用并发名额

`runtime.handleWithInvocation` 持有服务商并发名额直到 handler 返回。
原来三种客户端编码器直接调用 `Write`/`Flush`，忽略错误，也没有单次写入
期限。`context.WithTimeout` 只能取消上游请求，不能让正在阻塞的客户端
socket 写入立即返回。默认 HTTP `WriteTimeout` 为零，因此非正常客户端
可能一直占据槽位，后续请求得到 `provider_busy` 并进入客户端重试。

新增独立 `internal/httpstream` I/O 层：每次写入或 Flush 最多 30 秒，取消
请求会立即设置底层写入期限，写入与 Flush 错误都会向上传播。包装层补齐
ResponseController 穿透接口。三种编码器共用此机制，Unary 响应也有写入保护。

验证包括真实 TCP 客户端连接后不读响应：即便连接保持打开，请求也能失败
退出、停止上游、释放名额，后续请求正常返回。

### 2. 超时、异常断流可能被包装成成功结束

原来事件通道关闭时，编码器会生成 `[DONE]` / `response.completed` /
`message_stop`，没有区分正常结束与取消。上游错误帧和 JSON 解析失败还会
被忽略。客户端可能持续等待实际内容，或将不完整结果当成一次成功调用。

现在只接受明确的完成事件；异常关闭保留错误原因，已经开始的 SSE 响应
发送对应协议的错误事件。上游错误帧立即中止；解析器使用有大小上限的
Scanner，并在取消时关闭正在读取的响应体。取消回调和解析器退出共用一次性
关闭操作，避免并发重复 Close；该路径和工具拼接测试已重复执行 30 次 race 检测。

### 3. 缺少首 token 和输出停顿的独立期限

原来只有默认 120 秒的上游总期限。用户为长上下文增加总期限后，没有
输出的连接也会长期占位。只有心跳的流在诊断上尤其不明确。

新增 `first_token_timeout` 与 `stream_idle_timeout`，默认均为 60 秒。
心跳和角色帧不计为输出，文本、思考及工具调用进展才重置期限。
错误码区分首 token、流空闲、总期限、客户端取消和下游写入失败。
具体配置和兼容性说明见 [streaming-engine.md](streaming-engine.md)。

### 4. 每条请求重复 bcrypt，突发流量消耗鉴权 CPU

原来数据面每次按顺序检查所有启用的密钥并执行 bcrypt，发生在服务商并发
限制和上游超时之前。相同密钥的并发调用也重复计算。

新增最多 256 项的成功校验缓存，仅保存指纹及匹配索引。指纹包含密钥哈希、
启用状态和顺序；实际名称、RPM、模型权限仍读取当前请求的配置。同一指纹
的冷请求共享一次验证，最多四个不同的冷验证任务并发执行，过载明确返回
503 和 `Retry-After: 1`。失败结果不缓存。

本机 Linux/ARM64 容器、Go 1.26.5、bcrypt 默认 cost 的微基准：旧的重复
校验约 70 ms/次，命中成功缓存约 0.35 μs/次。该数字仅衡量校验步骤，
不代表上游模型的 TTFT 提升比例。

### 5. 修改并发上限没有真正作用于运行中的限流器

原来每个服务商首次请求创建一个固定容量 channel，修改配置后仍使用旧
channel。改为按服务商维护活动计数；新的请求使用当前配置的上限，降低
上限时仍计入已运行请求，不打断既有请求。

### 6. 并行工具调用的流式拼接会损坏 Agent 收到的参数

OpenAI Chat 编码器曾将所有工具调用输出为 `index: 0`。SDK 按 index 合并
delta 时，会把不同工具的 ID、名称与 JSON 参数混在一起。Anthropic 上游
的工具参数 delta 还重复携带完整 ID/名称，转换为 Chat 后 SDK 会把它们
重复拼接。

现在为各个 IR 工具索引分配独立、连续的 Chat 索引，支持交错参数分片；
Anthropic 工具标识只在起始事件给出，后续 delta 只携带参数分片。回归测试
按 SDK 的实际拼接方式验证两条交错工具调用及 Anthropic 到 Chat 的转换。
这个问题会破坏 Agent 的工具执行，但不能据此断言它就是现场 TTFT 等待的原因。

## 验证范围

- 三种协议的写入失败、Flush 失败及无完成事件的断流。
- 首 token、空闲、总期限、客户端取消的独立测试。
- 上游不发响应头、仅发心跳、输出中断、SSE 错误帧的重复失败及恢复。
- 真实 TCP 下游不读取响应的阻塞与释放测试。
- 五轮各 32 个并发请求，验证过载有界、请求全部结束、容量恢复。
- 密钥缓存的并发合并、容量、取消、撤销、轮换、RPM 和模型权限验证。
- 并行工具参数隔离、非连续源索引映射、跨协议工具标识不重复拼接。
- Go race 检测、全量 Go 回归、静态检查及 Windows CI。

桌面 CI 保留 Windows 安装 EXE 和 macOS DMG 作为 7 天有效的测试产物，
方便现场试用；它们不自动成为正式 Release。

## 审查边界

现有可观测性持久化通过有界 AsyncRecorder 执行，不直接在模型请求链路
同步写 SQLite；实时事件投递也使用有界队列。本轮没有把这两处误判为
数据库写锁造成的全局阻塞。已有 SQLite WAL 和多连接 busy timeout 测试
通过，所用驱动版本确实支持当前 DSN 参数。

尚未在用户的 Windows + Hermes + 实际上游组合进行现场复测。Windows
CI 可以验证系统行为和安装产物，但不能替代公司网络、代理和真实模型服务
的现场条件。后续如仍遇到等待，可用新增错误码、请求 ID、调用来源和服务商
定位阶段，无需先提供截图。
